# SF-150 — unblocking `factory start` on the real host

`./dev factory start` answered

```plain text
BLOCKED: Factory readiness checks are incomplete. Run './dev factory status' for the current state.
```

while `./dev factory status` reported the Bridge healthy, the primary provider
available and DF-1 next. The Owner had no way to tell what was unmet.

## Root cause

Two required preflight checks were `unknown`, not `unmet`:

```plain text
UNMET: {"check": "EVIDENCE_CORE_HEALTH", "detail": "no evidence_core report was supplied",
        "evidence_class": "not_run", "required": true, "state": "unknown"}
UNMET: {"check": "CONTEXT_BROKER_HEALTH", "detail": "no context_broker report was supplied",
        "evidence_class": "not_run", "required": true, "state": "unknown"}
```

`FactoryLifecycle._load_reports` runs each sibling repository's own
`./dev health`. Both are `docker compose run`, and the container runtime was not
running on this host:

```plain text
failed to connect to the docker API at unix:///Users/karlosabay/.orbstack/run/docker.sock;
check if the path is correct and if the daemon is running
```

`_load_reports` dropped the failed command with a bare `continue`, so the reason
never reached the Owner, and `_plain_preflight_blocker` had no mapping for either
check and fell through to its generic sentence.

With the runtime started, and nothing else changed, the same preflight and the
same shift gate both pass:

```plain text
PREFLIGHT ready: True   states: {'met': 26, 'unmet': 0, 'unknown': 0}
GATE ready: True
```

So the checks were not the defect. They are load-bearing: DF-1's own declared
acceptance gates, `factory-prototype-lab ./dev check` and `./dev test`, are
`docker compose run` as well. A Factory that cannot reach the container runtime
cannot re-derive DF-1's gates either, and `not_run` is a failure. The defect was
the dead-end message.

## Change

| file | what |
|---|---|
| `factory_controller/factory.py` | `_load_reports` keeps why a health command failed; `_plain_preflight_blocker` names the container runtime, the service, or the unmapped check; `status` points at the command that recovers an inconsistent state |
| `tests/test_factory_lifecycle.py` | five tests, and a `FakeHost` that answers `./dev health` |

`_plain_preflight_blocker` now has no dead end. Anything it cannot phrase
specifically is reported by check name rather than as "readiness checks are
incomplete".

`status` previously offered `./dev factory start` to repair an inconsistent
service/durable-state combination. Live dogfood proved `start` could not perform
that repair and `./dev factory stop` did, so `status` now names `stop` followed
by `start`. Both are existing commands; no new recovery ritual was added.

## What the unblocked path then found

`factory start` reaching `FACTORY READY` let DF-1 be dispatched for the first
time. Two further defects sat on that path, each fixed at its own layer.

### 1. The bridge's response could not be read

The supervisor's first cycle settled DF-1 `refused` with
`EXECUTION_MODE_UNPROVEN: layer reported unknown`. Running the same invocation
by hand shows why:

```plain text
TypeError: BridgeResponse.__init__() got an unexpected keyword argument 'process_started'
  -> BridgeRefusal: MALFORMED_BRIDGE_RESPONSE
```

`factory-bridge` added `process_started` and `selection_trace` to
`BridgeResponse` additively, under the same declared `schema_version` `1.0`,
and seals its response digest over both. `factory-evidence-core`'s mirror of
that dataclass never gained them, so every live response was rejected before
any of its content was read. Fixed in `factory-evidence-core`
`93c37f927a43304fab37ca5b79906825b51d2a14`; `./dev test` 429 tests OK,
`ACCEPTED dffb93a7…`, `ENVELOPES PASSED 06a15454…`,
`BASELINE compatible_post_baseline_hardening` — all unmoved.

### 2. The contained provider could not start

Underneath that, the bridge had already dispatched. Its own lane record:

```plain text
state: uncertain   process_started: true   process_exit_status: 1
selection_trace: ["codex-primary:selected"]
uncertain_reason: contained provider exited non-zero (1)
provider.stderr.log:
  Traceback (most recent call last):
    File "<string>", line 1, in <module>
  FileNotFoundError: [Errno 2] No such file or directory
```

The provider ran for 20 milliseconds. `lanes._GATE_CODE` reaches the process
through `os.execv`, which performs no PATH search, and
`containment.sandbox_argv` handed it a bare `sandbox-exec`. So no contained
provider could ever have started on this host. Fixed in `factory-bridge`
`9fd6756b7b8fb0bac926c447ed7a8ad3226fe6fe`, and proven both ways against the
installed bridge at `/Users/Shared/factory/lib`:

```plain text
bare name (the shipped defect): (1, '', ['FileNotFoundError: [Errno 2] No such file or directory'])
resolved by sandbox_argv     : (0, 'contained', [])
```

The installed receipt now reads `source_sha: 9fd6756b…`.

## Remaining blocker

DF-1's mission row is `refused`, and `refused` is in
`portfolio.TERMINAL`. `Portfolio.next_mission` therefore treats DF-1 as settled
and offers DF-2, which `factory run` refuses at intake:

```plain text
Next: DF-2, in factory-bug-lab
BLOCKED: The evidence layer does not admit the capability this project is
registered for, so the mission cannot be authorized.
```

So a mission refused by an infrastructure defect consumes its portfolio slot
exactly as a completed one does, and the frozen portfolio offers no retry.
Both defects above are fixed and the host is ready, but DF-1 cannot be
re-offered without a decision about whether an infrastructure refusal settles a
portfolio mission. That decision belongs to the portfolio's owner, not to this
task's scope guard.
