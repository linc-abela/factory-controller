## The defect, in the Owner's own words

`./dev factory status --watch` rendered this over a product mission that was
executing:

```
Attention: The DF-1 validation mission needs Owner attention before the Factory
can continue (ACCEPTANCE_GATE_FAILED: dev-check, dev-test).
Automatic validation is paused until the Owner reviews it.
```

Every clause of that is false about the current state and true about a frozen
internal portfolio. `_work_summary` read `shift.slots(entry)` — the first
dogfood portfolio — and nothing else. A product mission is named by the Owner
one package at a time, so it is in no portfolio and never will be; the status
surface therefore had nothing to say about it and said the last thing it knew.

`cycle` deliberately steps past that same escalation (`factory.py`, the comment
above `blocked = None if queued.ok else queued`) precisely so already-admitted
work keeps advancing. So the two halves of the Factory disagreed: execution
advanced the product and observation reported a paused Factory.

## The change

`factory.py` only. `_product_summary()` takes the status headline whenever a
mission exists under the product run contract's project, read from rows the
engine itself writes:

| line | source |
|---|---|
| work item + lifecycle state | `missions.payload.work_item_id`, `missions.state` via `PRODUCT_LIFECYCLE` |
| `Stage:` | `store.step_records()`, latest by `updated_at` |
| `Provider:` | `store.route_history()['selected_provider_profile']` |
| `Attention:` | `missions.terminal_reason`, only for `shift.UNSUCCESSFUL_MISSION_STATES` |
| `History:` | the same `_first_autopilot_attention` the autopilot reads, demoted |

`work_state` is `pending` while the mission is live, `complete` when it
completed, `attention` only when the *product* mission itself stopped — which
is what `--watch` keys off.

Not changed: `cycle`, `_queue_next`, `_first_autopilot_attention`, the shift
plane, the supervisor, or any durable row. `_work_summary` is untouched and
still owns the surface when no product mission exists.

## Recorded, not fixed

`shift.slots()` resolves a mission to its slot as
`key if key in refs else key.split(":", 1)[0]`. For a colon-bearing reference
like `lodus-casino:build` that yields `lodus-casino`, so the row would be
dropped. Harmless today — `slots()` is only ever called with the frozen
portfolio, whose references are colon-free, and this change reads product
missions from the store directly rather than through it. It is a real trap for
anyone who later puts a product work item in a portfolio.
