## The defect, in the Owner's own words

`./dev factory status --watch` rendered this over a product mission that was
executing:

```
Attention: The DF-1 validation mission needs Owner attention before the Factory
can continue (ACCEPTANCE_GATE_FAILED: dev-check, dev-test).
Automatic validation is paused until the Owner reviews it.
```

Every clause of that is false about the current state and true about a frozen
internal portfolio. `_work_summary` read `shift.slots(entry)` — the first
dogfood portfolio — and nothing else. A product mission is named by the Owner
one package at a time, so it is in no portfolio and never will be; the status
surface therefore had nothing to say about it and said the last thing it knew.

`cycle` deliberately steps past that same escalation (`factory.py`, the comment
above `blocked = None if queued.ok else queued`) precisely so already-admitted
work keeps advancing. So the two halves of the Factory disagreed: execution
advanced the product and observation reported a paused Factory.

## The change

`factory.py` only. `_product_summary()` takes the status headline whenever a
mission exists under the product run contract's project, read from rows the
engine itself writes:

| line | source |
|---|---|
| work item + lifecycle state | `missions.payload.work_item_id`, `missions.state` via `PRODUCT_LIFECYCLE` |
| `Stage:` | `store.step_records()`, latest by `updated_at` |
| `Provider:` | `store.route_history()['selected_provider_profile']` |
| `Attention:` | `missions.terminal_reason`, only for `shift.UNSUCCESSFUL_MISSION_STATES` |
| `History:` | the same `_first_autopilot_attention` the autopilot reads, demoted |

`work_state` is `pending` while the mission is live, `complete` when it
completed, `attention` only when the *product* mission itself stopped — which
is what `--watch` keys off.

Not changed: `cycle`, `_queue_next`, `_first_autopilot_attention`, the shift
plane, the supervisor, or any durable row. `_work_summary` is untouched and
still owns the surface when no product mission exists.

## Recorded, not fixed

`shift.slots()` resolves a mission to its slot as
`key if key in refs else key.split(":", 1)[0]`. For a colon-bearing reference
like `lodus-casino:build` that yields `lodus-casino`, so the row would be
dropped. Harmless today — `slots()` is only ever called with the frozen
portfolio, whose references are colon-free, and this change reads product
missions from the store directly rather than through it. It is a real trap for
anyone who later puts a product work item in a portfolio.

## What was broken between "mission finished" and "Owner can judge"

Four defects, all reproducible, all fixed.

**1. The product's review environment was never registered.** The run contract
names `lodus-casino-review` and `_provision_product_store` created the project
policy and the supervisor policy but no environment. The lab path registers its
own; this one was missed, so the first release deployment of the first real
product had nowhere to go. The production environment stays unregistered on
purpose: it is gated, reached only through an Owner Validation this path stops
short of, and an environment nothing can deploy to is a claim rather than a
provision.

**2. Nothing carried a finished mission to a Release Candidate.** The execution
layer could already mint an immutable artifact identity from a candidate commit
(`factory_bridge.artifact.build`) and `release.py` could already seal an RC and
record a review deployment. No code joined them, so the terminal state of a
successful product run was a commit on a lane reference plus an operator
expected to hand-author a release bundle. `./dev factory review` is that join.
It adds no rule: every bundle field is a durable row, the artifact is built by
the layer that owns the project registry, and every refusal is raised by the
release plane or the production ledger.

**3. No independent QA question was ever asked of a product candidate.** The
acceptance gates run from the *candidate's own checkout*, so a provider that
relaxed the script it is judged by would pass gates that no longer mean what
the contract declared — with every other record in the run still green. The
review now refuses a candidate whose recorded change set touches the contract's
`acceptance_gate_source`, and refuses equally when the change set was never
recorded: an unanswerable question is not a pass. For this candidate the
boundary held — neither `dev` nor `evaluate.mjs` is in the change set.

**4. A second review of one candidate was a hard refusal.** Found by running it
on the host, not by reading it: `./dev factory review` a second time returned
`RC_IDENTITY_MISMATCH`. `bundle_digest` is taken over every bundle field and
the RC id is derived from the candidate commit, so a provenance timestamp read
from "now" gave one id different bytes on every invocation. The unit test had
missed it because its two calls landed in the same second — the same luck that
decided a gate in SF-157. Fixed twice over: provenance now reads the mission's
settle time, and a review recognises an RC already sealed for its candidate and
artifact rather than offering that id a second set of bytes. A *different*
artifact still reaches `seal` and is still refused there. Verified live: four
reviews, one RC, one review deployment.

A fifth, smaller one: `status` told the Owner the mission finished and left
them to learn elsewhere that a verb existed to make it reviewable. It now names
the verb before a seal exists and the RC, artifact and surface after one.

## The surface is local, and that is the contract's own choice

`release._surface` accepts an HTTPS target or an explicit loopback one and
refuses everything else. This Factory has no authorized HTTPS target:
`linc-abela/lodus-casino` is private, `repos/.../pages` is 404, and
`gh api user` returns `plan: null` under a token without `user` scope, so the
free-plan constraint cannot even be measured here. Publishing the repository or
enabling Pages is an Owner act with a visibility decision behind it.

So the review is served on loopback, from the sealed artifact's own bytes —
which is what makes the digest an Owner validates the digest that would be
promoted, the invariant the package states about its own release. The Owner
starts and stops it; nothing here installs a service.

## Recorded, measured, and deliberately not changed

Two `uncertain` lanes — one per lab, `fln_factory-bug-lab_decfd970a84ba6d6de3fd5ec16`
and `fln_factory-prototype-lab_a13362a9bf0840ff8a19` — permanently hold 2 of
the bridge's 4 global slots. This is SF-157's recorded finding: `uncertain` is
in both `ACTIVE_STATES` and `PRESERVED_STATES` and no verb resolves one.
Measured here rather than assumed: `lodus-casino` holds **0** of its 2 project
slots, so the product path is not blocked. Separating "unresolved evidence"
from "occupied slot" is a change to a declared fail-closed contract on the
internal dogfood seam, which is not this sweep's to make.

`factory_bridge.artifact.publish_candidate` would push the candidate to the
project's own remote under `refs/factory/candidates/`. That is an irreversible
effect on somebody else's server and is not needed for a local review, so it
was not done.

A reinstall regression was not exercised: `./dev factory install` resets
`capabilities.json` to the shipped empty file every time, and running it while
the Owner's product sits ready for review would revoke the `development`
admission for no gain. Exercised where safe, as the task asks; skipped here,
and said so.
