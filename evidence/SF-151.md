# SF-151 — retrying an infrastructure-refused portfolio slot

DF-1 settled `refused` on the first live dogfood dispatch with

```plain text
EXECUTION_MODE_UNPROVEN: layer reported unknown
```

which SF-150 traced to two defects in the seam under the Controller, both since
fixed. `refused` is in `store.TERMINAL`, so `shift.TERMINAL_MISSION_STATES`
read the slot as settled and `Portfolio.next_mission` offered DF-2 — a mission
whose own capability the evidence layer did not admit. The first dogfood
mission was therefore unreachable by any Owner command.

## Root cause

The portfolio conflated two things that had never needed distinguishing while
every slot held at most one mission:

- a **slot** is the position a frozen portfolio names;
- a **mission** is one attempt at it.

`ShiftPlane.outcomes` returned mission states keyed by slot reference, and
`next_mission` read that mapping as the slot's own settlement. So the answer to
"has this slot been judged?" was actually the answer to "did the last attempt
stop?" — and an attempt that stopped because the execution layer could not
serve it never judged the work at all.

The narrow reading — "`refused` should not be terminal" — is wrong and the
brief rules it out. A deterministic policy or safety refusal is a real answer
about the mission's own frozen inputs and must stay settled. The distinction is
not in the *state*, it is in the *reason*.

## The retry classification rule

`shift.retry_classification(state, terminal_reason, attempts)` returns exactly
one of six classes, and only `retryable_infrastructure` admits another attempt.
Three conditions must all hold, and each is read from a decision another module
already made rather than re-derived here.

**One. The state must be `refused`.** `engine.work_once` writes `refused` only
while the mission is still `dispatching`:

```plain text
target = "refused" if current and current["state"] == "dispatching" else "failed"
```

The transition to `dispatched` requires a `candidate_sha`. So a refused mission
recorded no candidate and nothing downstream was built on one. `failed`,
`escalated` and `cancelled` mean the mission got further, or that a person owns
it now; all three classify as `settled` and are never retried. That invariant
is pinned by `test_a_refused_mission_never_recorded_a_candidate`, which drives
a real Controller past the boundary and asserts `failed`.

**Two. The reason must be an execution-layer fact.** The allowlist is
`store.INFRASTRUCTURE_REASON_PREFIXES`. Everything else is a verdict about the
mission's own frozen inputs — a denied profile, an invalid policy, an undeclared
gate, a spent ceiling — and those are deterministic in the strict sense: the
same inputs reach the same answer, so a retry is a slower way of being refused
twice. The default is **final**; the allowlist is the only way out of it.

**Three. The reason must not name a possible side effect.**
`store.SIDE_EFFECT_POSSIBLE_PREFIXES` holds `PROVIDER_SWITCH_AFTER_`, which
`engine` writes exactly when `gateway.may_reroute` refused a second dispatch
because the layer could not prove no process started. A portfolio that retried
one of those would be overruling a safety decision from one layer up.

Plus the bound: `shift.MAX_SLOT_ATTEMPTS = 3`, counting the first, after which
the slot is `attempts_exhausted` and settles for good.

| class | meaning |
|---|---|
| `retryable_infrastructure` | refused, execution-layer reason, no side effect possible, attempts remain |
| `not_settled` | no attempt has reached a terminal state |
| `settled` | terminal in a state other than `refused` |
| `deterministic_refusal` | refused for a reason about the mission itself |
| `side_effect_possible` | infrastructure, but a provider effect may have happened |
| `attempts_exhausted` | eligible but out of attempts |

### One definition, not a second one

`INFRASTRUCTURE_REASON_PREFIXES` moved into `store`, beside the state
vocabulary it qualifies, because two planes now read it for two decisions — the
supervisor's project suppression and this retry rule — and a private copy in
each is how they drift apart. `supervisor.INFRASTRUCTURE_PREFIXES` is now the
same object; `test_the_infrastructure_vocabulary_has_one_definition` asserts
identity, not equality.

Four seam entries were added to it from the live dispatch:
`EXECUTION_MODE_UNPROVEN`, `EXECUTION_MODE_MISMATCH`,
`IDEMPOTENCY_KEY_UNPROVEN`, `IDEMPOTENCY_KEY_DIVERGED`. Every one is a
statement about what the *layer* proved, raised by `engine._verify_receipt`;
none is a reading of the mission. **This widens project suppression as well**:
a run of seam failures now moves the supervisor's counter instead of resetting
it. That is the same fact answering the same question in both places, which is
why the set is shared rather than forked.

## Identity, idempotency and lineage

A retry is a **new mission bound to the same work item**, not a reopened one.
`dogfood_intake.build` takes an `attempt` and the number reaches the mission's
identity through exactly one field:

```plain text
policy_identity = "<portfolio_ref>:<mission_ref>"          # attempt 1
policy_identity = "<portfolio_ref>:<mission_ref>#<n>"      # attempt n > 1
```

`policy_identity` is inside the context manifest, so the manifest hash differs
per attempt, so the idempotency key differs per attempt — while still carrying
the shape `routing.expected_idempotency_key` mandates and Evidence Core refuses
anything else for:

```plain text
DF-1:09ac38ca37655c0ab3d9e2c4d41e46e486ab5c98c093fc4d69729e092be8432c   attempt 1
DF-1:4c63b401847eeab3a3e9af2e35686ce40c062131aa0f41ab77ff90755a42d7a4   attempt 2
```

`work_item_id` stays `DF-1` in both. The slot *is* the work item; a second name
for it would be a second work item, and `ShiftPlane.slots` resolves both keys to
the same slot with no new matching rule.

Why the key must differ rather than be reused: the execution layer memoises a
response per idempotency key under `~/.factory-bridge/requests/<key>.json`, so
a stored refusal answers forever for the key it was stored under. Reusing the
key would replay the refusal; a new key leaves the old memo untouched, so the
first attempt is neither re-run nor overwritten.

Lineage is durable and readable without recomputing a hash: the payload carries
`attempt`, and `ShiftPlane.slots` orders attempts by `created_at, rowid` — that
ordering is now load-bearing and was previously whatever SQLite returned last.

Attempt 1 is byte-identical to what `build` produced before retries existed, so
no mission already in a ledger can have its identity move under it.

## History is preserved

`_mission_path` gained the attempt. Attempt 1 keeps its original filename;
attempt *n* writes `df-1-attempt-<n>-admission.json` and
`df-1-attempt-<n>-result.json`. A retry that wrote to the same two paths would
overwrite the admission document and the provider result of the attempt it is
replacing — the history the retry exists to preserve.

## What the Owner sees

`outcomes()` stays truthful about the ledger: a retryable slot still reports
`refused`, because that mapping is also what `missions_in_flight` and the
Owner's brief are read from, and a settled mission reported as unsettled would
count as running. The retry reading is separate — `slots()` / `retryable()` —
and is passed explicitly into `next_mission`, `complete`, `admission` and
`brief`. Every one of those defaults to the empty set, so a caller that has not
classified anything gets the strictly serial rule it had before.

## Remaining blockers before a successful DF-1 settlement

None in the control plane. The retry is admitted and the supervisor's cycle is
what settles it; the outcome of that dispatch is the execution leg's subject,
not this one's. The one normal Owner command for a further live retry, if the
attempt refuses again on infrastructure, is `./dev factory run`.
