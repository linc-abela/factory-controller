# SF-157 — the Phase-1 path, and the five defects that were all one shape

`./dev factory status --watch` reported, on a Factory it also called READY:

```plain text
Attention: The DF-1 validation mission needs Owner attention before the Factory
can continue (ACCEPTANCE_GATE_FAILED: dev-check, dev-test).
```

DF-1 mutates nothing. Its two gates are `./dev check` and `./dev test` at
`factory-prototype-lab` 229b923b, and the frozen portfolio's own rationale
records that both exit 0 there. Measured again on this host, from an ordinary
shell, they still do. So the mission was blocked by a verdict that was not
true.

Five defects were found. Every one of them is the same mistake in a different
organ: **a fact about the environment was treated as a fact about the work.**

---

## 1. The supervisor job named no PATH

`factory_controller/factory.py` `_service_plan`

The supervisor LaunchAgent's `EnvironmentVariables` carried the Context Broker
command and cache and nothing else. launchd hands such a job its own default:

```plain text
default environment = { PATH => /usr/bin:/bin:/usr/sbin:/sbin }
```

Two things live outside that PATH, and both are load-bearing.

**The acceptance gates.** Both labs' evaluators are one line —
`exec docker compose run --rm lab ...` — and `docker` is `/usr/local/bin/docker`
on this host. Reproduced exactly:

```plain text
$ env -i HOME=$HOME PATH=/usr/bin:/bin:/usr/sbin:/sbin ./dev check
./dev: line 9: exec: docker: not found
exit=127
$ ./dev check
exit=0
```

The evaluate step recorded that 127 as a gate result:

```plain text
{"gate_id": "dev-check", "passed": false, "exit_code": 127,
 "detail": ".../factory-prototype-lab/dev check"}
```

which `engine._gate_refusal` correctly turned into `ACCEPTANCE_GATE_FAILED:
dev-check, dev-test`. Nothing in that chain is wrong. The gate ran, it exited
non-zero, and the engine reported it. The mission was blocked by the truthful
report of a meaningless measurement.

**The provider.** `factory cycle` calls `_check_primary_and_containment`, which
runs `factory-bridge/dev readiness` in process. `providers.json` named `codex`
as a bare command, resolved with `shutil.which`, and `codex` is in
`~/.local/bin`:

```plain text
$ env -i HOME=$HOME PATH=/usr/bin:/bin:/usr/sbin:/sbin ./dev readiness
codex-primary unavailable | provider executable is unavailable | None
```

so every unattended cycle exited 1 with
`BLOCKED: Codex is unavailable. Complete its sign-in, then retry start.` —
about a provider that was signed in and available.

**Why it appeared after a host refresh.** A LaunchAgent bootstrapped from an
interactive shell can carry that shell's environment; one bootstrapped by
launchd after a reboot cannot. The job had worked for as long as nobody had
restarted the host. The Bridge's own job definition has always named its PATH
(`factory_bridge.install.launchagent_plist`); this one did not.

**Fix.** `SUPERVISOR_PATH_DIRS` plus the interpreter's directory and the
Owner's `~/.local/bin`, written into the job. The environment is inside
`activation.ServicePlan.digest`, so the installed job is drift-checked against
it like every other plan field, and `_install_supervisor_definition` already
boots out a reinstalled job so launchd picks the new definition up.

## 2. An attention on one slot stopped every other mission

`factory_controller/factory.py` `cycle`

```python
queued = self._queue_next(contract, entry, doctor, grant, owner_action=False)
if not queued.ok or queued.state == "complete":
    return queued
report = self.supervisor.cycle(AUTOPILOT_WORKER_ID)
```

`_queue_next` runs the autopilot blocker check *before* it returns a mission,
so an attention returned from the first line and the supervisor never ran at
all. The blocker is about handing off the **next** slot; what it actually
stopped was the execution of everything already admitted.

Live consequence: DF-3 had been admitted by the Owner's own
`./dev factory run` — a verb that deliberately does not consult the autopilot
blocker, because the Owner naming the next mission is a decision, not a guess —
and then sat `admitted` for six hours while `store.schedule_preview()` answered
`SCHEDULED` and no cycle ever claimed it. A mission past the dispatch boundary
would have been worse than stranded: unreconciled, with reconciliation waiting
on a person.

**Fix.** The cycle advances what is already admitted, hands off nothing new
while a blocker stands, and returns the blocker with the cycle report attached.
`test_an_attention_stops_the_next_handoff_and_not_the_admitted_work` builds the
live shape — an escalated slot reached through the ordinary transitions, plus
an Owner-submitted successor — and fails on the previous code with
`'admitted' == 'admitted'`.

## 3. A gate outcome carried a number and no evidence

`factory_controller/stage1_adapter.py` `_run_gate`

`subprocess.run(..., capture_output=True)` captured stdout and stderr and threw
both away. So `exit_code: 127` from a missing container runtime and
`exit_code: 1` from a genuinely failing suite were the same durable record, and
telling them apart meant re-running the gate by hand in the right environment.
This is the SF-150 shape — that root cause was also one line of dropped stderr.

**Fix.** A bounded `stderr_tail` travels with the outcome, `not_applicable`
when the process said nothing. The exit status is still recorded exactly as
observed: DF-2's stop conditions forbid rewriting a non-zero gate as met *or as
any absence word*, and a gate that cannot find its tooling exits like any other
failing command. What changed is that the record now says why.

## 4. The running Bridge served files that had been replaced under it

`factory-bridge` `src/factory_bridge/{paths,cli,install}.py`

`service.Bridge` is constructed once, from `providers.json`, `projects.json`
and `capabilities.json` as they are at that moment. `install` and
`capability admit` rewrite those files. Nothing reloads the service, and every
diagnostic is a short-lived process that re-reads them — so the tooling and the
server disagree in the one direction nobody checks.

Both halves were live.

**The capability.** The bridge daemon started `2026-08-31 23:45:07`. The `bug`
admission was written `2026-09-01 10:27:50`. `./dev doctor` reported
`serving: ["bug", "prototype"]` throughout. The serving process refused every
`bug` mission:

```plain text
"refusal_code": "UNSUPPORTED_CAPABILITY",
"refusal_message": "this bridge does not serve that capability"
```

which the Controller records as `EXECUTION_MODE_UNPROVEN: layer reported
unknown` — the code three DF-2 attempts had already settled on. Restarting the
service changed the refusal, in one step, to a different one.

**The model.** DF-1's lane on the *old* process ran `gpt-5.6-sol` at reasoning
effort `medium`, while the installed `providers.json` named `gpt-5.6-luna` at
`max`. The file had been replaced under a process that kept serving what it
read.

The admission overlay is deliberately not written into `providers.json` —
`capability.py` says so, and it is right — so the fix is not to rewrite those
files. It is to make the difference reportable.

**Fix.** `serve` writes `~/.factory-bridge/serving-receipt.json` recording the
three registry digests and the capability set the process bound, before it
answers anything. `install.doctor` reports `serving_drift` by comparing that
receipt with the files that are there now; an absent receipt is
`not_applicable`, never agreement. The Controller treats serving drift as a
reload — the files on disk are already what the Owner wants served, only the
process is behind — and `_admit_required_capability` reloads the service the
admission was meant to widen.

## 5. Two Codex CLIs, and the readiness probe could not tell them apart

`factory-bridge/providers.json`

This host carries two:

```plain text
/opt/homebrew/bin/codex        -> codex-cli 0.142.5
/Users/karlosabay/.local/bin/codex -> codex-cli 0.144.1
```

`providers.json` named `codex`, a bare command, so which one the Factory used
was decided by the PATH of whoever ran `install` — and that answer was then
frozen into the LaunchAgent's own PATH. The receipt written on this host
pinned the older one:

```plain text
"provider_executable": "/opt/homebrew/lib/node_modules/@openai/codex/bin/codex.js"
```

The readiness probe is `codex login status`, which exits 0 on both. So the
profile read `available`, `doctor` read healthy, and the mismatch appeared only
after a real dispatch had already started:

```plain text
ERROR: {"type":"error","status":400,"error":{"message":"The 'gpt-5.6-luna'
model requires a newer version of Codex. Please upgrade..."}}
```

recorded as `ADAPTER_UNAVAILABLE: contained provider exited non-zero (1)`.

**Fix.** `codex-primary` names an absolute executable. A name the host may
resolve two ways is not configuration. After reinstall the Bridge's own job
PATH leads with `~/.local/bin` and `resolved_executable` is the 0.144.1
release.
