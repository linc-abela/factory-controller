# SF-157 — the Phase-1 path, and the five defects that were all one shape

`./dev factory status --watch` reported, on a Factory it also called READY:

```plain text
Attention: The DF-1 validation mission needs Owner attention before the Factory
can continue (ACCEPTANCE_GATE_FAILED: dev-check, dev-test).
```

DF-1 mutates nothing. Its two gates are `./dev check` and `./dev test` at
`factory-prototype-lab` 229b923b, and the frozen portfolio's own rationale
records that both exit 0 there. Measured again on this host, from an ordinary
shell, they still do. So the mission was blocked by a verdict that was not
true.

Five defects were found. Every one of them is the same mistake in a different
organ: **a fact about the environment was treated as a fact about the work.**

---

## 1. The supervisor job named no PATH

`factory_controller/factory.py` `_service_plan`

The supervisor LaunchAgent's `EnvironmentVariables` carried the Context Broker
command and cache and nothing else. launchd hands such a job its own default:

```plain text
default environment = { PATH => /usr/bin:/bin:/usr/sbin:/sbin }
```

Two things live outside that PATH, and both are load-bearing.

**The acceptance gates.** Both labs' evaluators are one line —
`exec docker compose run --rm lab ...` — and `docker` is `/usr/local/bin/docker`
on this host. Reproduced exactly:

```plain text
$ env -i HOME=$HOME PATH=/usr/bin:/bin:/usr/sbin:/sbin ./dev check
./dev: line 9: exec: docker: not found
exit=127
$ ./dev check
exit=0
```

The evaluate step recorded that 127 as a gate result:

```plain text
{"gate_id": "dev-check", "passed": false, "exit_code": 127,
 "detail": ".../factory-prototype-lab/dev check"}
```

which `engine._gate_refusal` correctly turned into `ACCEPTANCE_GATE_FAILED:
dev-check, dev-test`. Nothing in that chain is wrong. The gate ran, it exited
non-zero, and the engine reported it. The mission was blocked by the truthful
report of a meaningless measurement.

**The provider.** `factory cycle` calls `_check_primary_and_containment`, which
runs `factory-bridge/dev readiness` in process. `providers.json` named `codex`
as a bare command, resolved with `shutil.which`, and `codex` is in
`~/.local/bin`:

```plain text
$ env -i HOME=$HOME PATH=/usr/bin:/bin:/usr/sbin:/sbin ./dev readiness
codex-primary unavailable | provider executable is unavailable | None
```

so every unattended cycle exited 1 with
`BLOCKED: Codex is unavailable. Complete its sign-in, then retry start.` —
about a provider that was signed in and available.

**Why it appeared after a host refresh.** A LaunchAgent bootstrapped from an
interactive shell can carry that shell's environment; one bootstrapped by
launchd after a reboot cannot. The job had worked for as long as nobody had
restarted the host. The Bridge's own job definition has always named its PATH
(`factory_bridge.install.launchagent_plist`); this one did not.

**Fix.** `SUPERVISOR_PATH_DIRS` plus the interpreter's directory and the
Owner's `~/.local/bin`, written into the job. The environment is inside
`activation.ServicePlan.digest`, so the installed job is drift-checked against
it like every other plan field, and `_install_supervisor_definition` already
boots out a reinstalled job so launchd picks the new definition up.

## 2. An attention on one slot stopped every other mission

`factory_controller/factory.py` `cycle`

```python
queued = self._queue_next(contract, entry, doctor, grant, owner_action=False)
if not queued.ok or queued.state == "complete":
    return queued
report = self.supervisor.cycle(AUTOPILOT_WORKER_ID)
```

`_queue_next` runs the autopilot blocker check *before* it returns a mission,
so an attention returned from the first line and the supervisor never ran at
all. The blocker is about handing off the **next** slot; what it actually
stopped was the execution of everything already admitted.

Live consequence: DF-3 had been admitted by the Owner's own
`./dev factory run` — a verb that deliberately does not consult the autopilot
blocker, because the Owner naming the next mission is a decision, not a guess —
and then sat `admitted` for six hours while `store.schedule_preview()` answered
`SCHEDULED` and no cycle ever claimed it. A mission past the dispatch boundary
would have been worse than stranded: unreconciled, with reconciliation waiting
on a person.

**Fix.** The cycle advances what is already admitted, hands off nothing new
while a blocker stands, and returns the blocker with the cycle report attached.
`test_an_attention_stops_the_next_handoff_and_not_the_admitted_work` builds the
live shape — an escalated slot reached through the ordinary transitions, plus
an Owner-submitted successor — and fails on the previous code with
`'admitted' == 'admitted'`.

## 3. A gate outcome carried a number and no evidence

`factory_controller/stage1_adapter.py` `_run_gate`

`subprocess.run(..., capture_output=True)` captured stdout and stderr and threw
both away. So `exit_code: 127` from a missing container runtime and
`exit_code: 1` from a genuinely failing suite were the same durable record, and
telling them apart meant re-running the gate by hand in the right environment.
This is the SF-150 shape — that root cause was also one line of dropped stderr.

**Fix.** A bounded `stderr_tail` travels with the outcome, `not_applicable`
when the process said nothing. The exit status is still recorded exactly as
observed: DF-2's stop conditions forbid rewriting a non-zero gate as met *or as
any absence word*, and a gate that cannot find its tooling exits like any other
failing command. What changed is that the record now says why.

## 4. The running Bridge served files that had been replaced under it

`factory-bridge` `src/factory_bridge/{paths,cli,install}.py`

`service.Bridge` is constructed once, from `providers.json`, `projects.json`
and `capabilities.json` as they are at that moment. `install` and
`capability admit` rewrite those files. Nothing reloads the service, and every
diagnostic is a short-lived process that re-reads them — so the tooling and the
server disagree in the one direction nobody checks.

Both halves were live.

**The capability.** The bridge daemon started `2026-08-31 23:45:07`. The `bug`
admission was written `2026-09-01 10:27:50`. `./dev doctor` reported
`serving: ["bug", "prototype"]` throughout. The serving process refused every
`bug` mission:

```plain text
"refusal_code": "UNSUPPORTED_CAPABILITY",
"refusal_message": "this bridge does not serve that capability"
```

which the Controller records as `EXECUTION_MODE_UNPROVEN: layer reported
unknown` — the code three DF-2 attempts had already settled on. Restarting the
service changed the refusal, in one step, to a different one.

**The model.** DF-1's lane on the *old* process ran `gpt-5.6-sol` at reasoning
effort `medium`, while the installed `providers.json` named `gpt-5.6-luna` at
`max`. The file had been replaced under a process that kept serving what it
read.

The admission overlay is deliberately not written into `providers.json` —
`capability.py` says so, and it is right — so the fix is not to rewrite those
files. It is to make the difference reportable.

**Fix.** `serve` writes `~/.factory-bridge/serving-receipt.json` recording the
three registry digests and the capability set the process bound, before it
answers anything. `install.doctor` reports `serving_drift` by comparing that
receipt with the files that are there now; an absent receipt is
`not_applicable`, never agreement. The Controller treats serving drift as a
reload — the files on disk are already what the Owner wants served, only the
process is behind — and `_admit_required_capability` reloads the service the
admission was meant to widen.

## 5. Two Codex CLIs, and the readiness probe could not tell them apart

`factory-bridge/providers.json`

This host carries two:

```plain text
/opt/homebrew/bin/codex        -> codex-cli 0.142.5
/Users/karlosabay/.local/bin/codex -> codex-cli 0.144.1
```

`providers.json` named `codex`, a bare command, so which one the Factory used
was decided by the PATH of whoever ran `install` — and that answer was then
frozen into the LaunchAgent's own PATH. The receipt written on this host
pinned the older one:

```plain text
"provider_executable": "/opt/homebrew/lib/node_modules/@openai/codex/bin/codex.js"
```

The readiness probe is `codex login status`, which exits 0 on both. So the
profile read `available`, `doctor` read healthy, and the mismatch appeared only
after a real dispatch had already started:

```plain text
ERROR: {"type":"error","status":400,"error":{"message":"The 'gpt-5.6-luna'
model requires a newer version of Codex. Please upgrade..."}}
```

recorded as `ADAPTER_UNAVAILABLE: contained provider exited non-zero (1)`.

**Fix.** `codex-primary` names an absolute executable. A name the host may
resolve two ways is not configuration. After reinstall the Bridge's own job
PATH leads with `~/.local/bin` and `resolved_executable` is the 0.144.1
release.

## 6. The Controller gave up before the work could finish

`factory_controller/adapter.py` `JsonProcessAdapter`

`timeout_seconds` defaulted to 300. The execution layer it waits on allows its
provider 3600 (`providers.json`), and a mission may declare three acceptance
gates at `gate_timeout_seconds` 1800 each. The Controller's own clock was
therefore guaranteed to fire first on any real mission — and what it wrote was
`ADAPTER_UNAVAILABLE`, a fact about the work.

Measured on the isolated validation run, from the ledger:

```plain text
11:30:55  CLAIMED_ATTEMPT_STARTED  admitted -> dispatching   DF-2 attempt 1
11:30:55  STEP_STARTED             dispatch
11:35:55  RETRY_SCHEDULED          dispatching -> admitted
          ADAPTER_UNAVAILABLE: Command '(...python3.14, ...)' timed out
11:35:56  attempt 2  -> refused    ADAPTER_UNAVAILABLE: LANE_ALREADY_ACTIVE
11:35:58  attempt 1  -> refused    ADAPTER_UNAVAILABLE: PROJECT_CAPACITY_EXHAUSTED
11:36:00  attempt 1  -> refused    ADAPTER_UNAVAILABLE: PROJECT_CAPACITY_EXHAUSTED
```

Exactly 300 seconds, and the provider process was still alive: `pid 48349`,
running the 0.144.1 binary in its lane, for six more minutes after the
Controller had already declared it unavailable. The retry was then refused by
the lane its own first attempt still held, and the slot's remaining attempts
were spent in five seconds on capacity the same run had just consumed. Three
attempts gone, and not one of them a statement about the mission.

DF-1 passed only because it happened to finish inside the five minutes.

**Fix.** `STEP_TIMEOUT_SECONDS = 7200`, which exceeds both ceilings the step
can legitimately wait on.
`test_a_step_may_take_longer_than_everything_it_waits_on` pins the
relationship — the longest gate list in the frozen portfolio times the mission's
own gate timeout — rather than the number.

## Reported, not fixed: an `uncertain` lane consumes its project's capacity forever

`factory-bridge` `src/factory_bridge/lanes.py`

`uncertain` is in both `ACTIVE_STATES` (so it counts against
`per_project_limit`, which is 2) and `PRESERVED_STATES` (so
`_recover_stale_locked` preserves it and never reclaims it). `cancel` on a
post-dispatch lane also ends `uncertain`, and `reconcile` explicitly "never
allocates". There is no verb that resolves one.

That is deliberate as a *safety* rule — a provider may have had an effect, so
the binding must never be dispatched again — and the identity check
(`_check_identity_conflicts`, which is what raised `LANE_ALREADY_ACTIVE`)
enforces exactly that, separately from capacity. But the consequence is that
**two aborted post-dispatch missions wedge a project permanently**, with no
Owner command to recover and no signal that it has happened. On this host:

```plain text
factory-bug-lab        1/2 consumed by fln_..._decfd970 (uncertain)
factory-prototype-lab  1/2 consumed by fln_..._a13362a9 (uncertain, 2026-08-31)
```

Both were produced by defects 5 and 6, so with those fixed the rate should fall
to aborts and crashes. It is left reported rather than fixed because the change
— separating "unresolved evidence" from "occupied slot" in the Bridge's
capacity accounting — is a change to a declared fail-closed contract, and
SF-157's scope explicitly stops short of governance. The ceiling is two per
project, which is why it did not stop this run.

## The proof

Run through `validation/phase1_validation.py`, which carries the four frozen
missions byte-identical under `SF-157-phase-1-validation-v3`, against an
isolated state directory and ledger, through the real Bridge over its real
unix socket, the real Codex provider, and the labs' real containerised
evaluators. Only the identities and the ledger are new; the code path is the
installed one.

The historical DF-1/DF-2 attempts on `~/.factory-controller/factory-controller.db`
were not touched: the validation run has its own database, and the new
portfolio reference gives every mission a new context identity and therefore a
new idempotency key, so no memoised Bridge response was replayed or
overwritten.

### What it did

```plain text
install   FACTORY INSTALLED
start     FACTORY READY
cycle-1   DF-1 completed  (attempt 1)          DF-2 admitted
cycle-2   DF-2 completed  (attempt 1)          DF-3 admitted
cycle-3   DF-3 completed  (attempt 1)          DF-4 admitted
cycle-4   DOGFOOD PORTFOLIO COMPLETE
exit=0
```

Four missions, four idempotency keys, one attempt each.

| slot | key | candidate |
|---|---|---|
| DF-1 | `DF-1:b09a0ea397b87e87…` | `095e9a52b6414c4bbb0ef14cc006bc4272ad9d89` |
| DF-2 | `DF-2:9146478420dbeefc…` | non-mutating |
| DF-3 | `DF-3:ed366e390c67073d…` | `751be6dcc302e7aa5c0721bd607ee8a6359fb04d` |
| DF-4 | `DF-4:2ee0a509f4f79ee7…` | `ee816e5c45a1eed7714c998060792a643c5dd4cb` |

### DF-2: the failure is recorded as a failure

```plain text
dev-check      passed=True   exit=0
dev-test       passed=True   exit=0
dev-reproduce  passed=False  exit=1   expected_failure=True  satisfied=True
```

The non-zero exit is preserved as a non-zero exit — not smoothed into a pass,
and not written as any absence word. The two passing gates are recorded
separately from the failing one. The mission completed because the *declared
expectation* was met, which is the whole of what DF-2 exists to prove.

### DF-3: the first mutating mission, checked against a known-good fix

Gates ran with `target: candidate`, `target_sha: 751be6dc`, in a detached
worktree — `/…/T/factory-candidate-0g2uigs2/checkout/dev {check,test,reproduce}` —
never the baseline. `dev-reproduce` moved from **exit 1 at 4072bfd7** (measured
directly on this host before the run) to **exit 0 at the candidate**.

The diagnosis is correct. `BookingLedger.reserve_batch` compared each request
against `available_at_start` rather than a running total, so 6 + 5 both passed
against a capacity of 10; the fix sums the batch before booking any of it. The
added regression was measured at the baseline in a detached worktree:

```plain text
AssertionError: ValueError not raised
Ran 4 tests   FAILED (failures=1)
```

so it fails at the baseline and passes at the fix, which is what the portfolio
asks for.

The rewritten `lab/reproduce.py` is not a weakened check: it exits 0 only when
the batch is *rejected* **and** the ledger is untouched, and exits 1 if the
batch is accepted. The gate flipped because the defect was fixed.

**One deviation, recorded rather than resolved.** The candidate also adds
`ROOT_CAUSE.md` at the repository root. DF-3's `evidence_required` asks for
"the root cause stated in writing" and does not say where; its `stop_conditions`
say "any change lands outside the lab package and its tests". Those two read
against each other, and the Factory's own gates cannot see the difference.

### DF-4: gates honest, improvement plane never reached

`dev-check`, `dev-test` and `dev-evaluate` all exit 0 against the candidate, so
the declared stop condition — `dev-evaluate` moving from 0 to non-zero — did not
fire. But the candidate is an **empty commit**: `git diff 229b923b..ee816e5c` is
empty. That is honest rather than broken. The frozen portfolio's own rationale
records that M3 is already implemented at 229b923b and all three gates already
exit 0 there, so there was no improvement for the provider to make.

What the run does **not** produce is the rest of DF-4's `evidence_required`: a
baseline measurement recorded before the candidate ran, a post-change
measurement of the same metric, and the promotion decision with its approval
reference. In the validation ledger, `experiments` is 0, `deployments` is 0,
and the improvement policy is provisioned `enabled: false`. The `factory cycle`
dogfood seam carries every slot through the ordinary mission pipeline; it never
touches the improvement plane. Wiring Stage 8 into the dogfood path is new
capability, not stabilization, so it is named here and left.

### Boundaries

Both labs are byte-identical to their frozen baselines, locally and on the
remote:

```plain text
factory-prototype-lab  local 229b923b…  origin/main 229b923b…  clean
factory-bug-lab        local 4072bfd7…  origin/main 4072bfd7…  clean
```

Every candidate exists only as `refs/factory/lanes/<lane_id>` in the registered
checkout. Nothing was pushed; `factory-bridge/src` contains no `git push` at
all.

### Restart, reinstall, and repetition

Every cycle above is a separate process reading the same durable ledger. After
the portfolio completed, a further `install` (which stops the Factory, as it
should), a `start`, and two more cycles produced:

```plain text
DOGFOOD PORTFOLIO COMPLETE
DOGFOOD PORTFOLIO COMPLETE
missions=4  distinct idempotency keys=4
```

No mission was created twice, no settled mission regressed into attention, and
`status` reads `Work: every first-dogfood mission has settled`.

The attention path was exercised too, in the run before the timeout fix: DF-2
spent its three slot attempts and the cycle returned

```plain text
FACTORY ATTENTION
The DF-2 validation mission needs Owner attention before the Factory can
continue (EXECUTION_MODE_UNPROVEN: layer reported unknown).
```

with `exit=1` — the bounded-retry rule (`MAX_SLOT_ATTEMPTS = 3`) holding and
stopping, rather than looping.
